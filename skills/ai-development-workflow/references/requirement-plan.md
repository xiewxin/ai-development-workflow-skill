## 來源與證據優先級

需求來源預設可為任務系統，也可直接來自原型、知識庫、表格或目前對話。來源衝突時依序採用：

1. 目前對話的明確說明。
2. 需求內容及驗收條件。
3. 原型、知識庫或表格。
4. 已驗證的程式碼、測試與實作文件。
5. 歷史計畫。

同一優先級內仍有衝突時，分別列出事實、影響與待確認問題，不自行選擇。

### 任務系統

閱讀標題、描述、預期結果或驗收條件、圖片、關聯資料、附件、全部留言，以及留言中的連結。只有下列情況才讀變更歷史：

- 目前內容彼此衝突。
- 有跡象顯示需求曾變更。
- 使用者明確要求追溯變更。

來源無法存取、附件不可讀或內容缺失時，在「待確認事項」列出缺口與影響，不猜測內容。

### 原型

原型閱讀範圍包含：

- 使用者提供連結所指向的頁面。
- 從該頁依互動可到達的頁面。
- 與同一流程直接相關的頁面。

若範圍不明或過大，先列出建議範圍與排除範圍，再只問一個最能界定範圍的確認問題。

## 主倉庫探索

預設目前工作目錄是主倉庫。依序閱讀並驗證：

1. 根目錄規範檔與貢獻、開發流程說明。
2. 目標範圍內既有的 `CONTEXT.md`、`CONTEXT-MAP.md` 與相關 ADR／決策文件。
3. 與需求相關的 `docs/agents/` 指南。
4. 實際程式碼、設定、路由或入口、資料流與測試。
5. 可能被 Git 忽略的 `docs/plans/` 文件。

`docs/plans/` 只代表歷史意圖，不可單獨作為現況證據。`docs/agents/` 也必須由目前程式碼與測試驗證；若內容不一致，在「現況與證據」指出文件漂移及其影響。

領域上下文與 ADR 只在檔案已存在且與目前需求、模組或資料流直接相關時讀取；不存在時不建立，不為補齊格式掃描全部決策歷史，也不新增必填章節。它們用來確認詞彙、邊界、非目標與既有取捨，仍須由目前程式碼、測試與有效需求驗證。若既有決策與目前需求或實作衝突且會改變範圍、合同或方案，在「待確認事項」列出文件位置、衝突、影響與建議處置，等待確認後再定案。

每筆證據先標示所屬「專案／倉庫」，再使用該倉庫內的相對路徑；必要時附類別、方法、設定鍵或測試名稱。不要使用本機絕對路徑，也不要貼大段程式碼或日誌。

## 責任與協作邊界

檔案級實作範圍依序由下列證據決定：

1. 使用者在目前對話明確說明的負責範圍。
2. 目前工作目錄的倉庫類型、根目錄規範、現有程式碼與測試。
3. 已取得且已驗證的其他專案資訊。

只對已授權且有倉庫證據的部分展開檔案級實作計畫、實作切片與執行指令。其他職能或專案以使用者流程影響、合同、依賴、協作事項與聯調驗收邊界表示；取得使用者明確授權及對應倉庫證據後，才展開其檔案、元件、技術棧或實作步驟。

責任邊界不明且會影響範圍、合同或交付時，將已查證據、具體缺口與影響列入「待確認事項」，不用假設補齊檔案級計畫。

## 跨專案邊界

只有發現具體跨專案缺口時，才詢問或探索其他專案，例如：

- client 存在但找不到 server。
- producer 存在但找不到 consumer。
- 需求依賴的資料表、Model 或 Repository 缺失。
- 只找到介面呼叫，找不到實作端。
- 已驗證鏈路只覆蓋完整流程的一段。

詢問時必須列出缺口、已查的專案／倉庫、倉庫內相對路徑、搜尋詞與現有證據。若未取得其他專案資訊，仍完成主倉庫可確認的計畫，將跨專案部分標記為待驗證，不以推測補齊。

跨專案預設只在主倉庫建立需求計畫；各專案分別維護自己的實作文件。

## Provider 橋接

目前對話、已載入能力、倉庫規範或活動產物顯示外部工作流時，先依[外部工作流適配與橋接指南](workflow-integration.md)選擇單一需求級主 Provider，再建立橋接。沒有外部工作流證據時，橋接模式只填一行「原生；無外部正式產物」，刪除完整映射表，不額外掃描或建立外部產物。

只有存在活動外部產物時才展開橋接映射。映射必須記錄：範圍／倉庫、能力、Provider、產物定位、狀態／完整性、唯一可寫所有者、讀寫權、更新關卡、同步方向與同步結果。產物定位使用倉庫內相對路徑或 tracker 識別字；外部 tracker 不要求虛構相對路徑，也不保存含敏感參數的完整網址。完整性只能是「完整、缺失、衝突、過時」之一，且缺失、衝突或過時項必須列出影響與補齊位置。

- 需求級主 Provider 定義整體流程、跨倉庫驗收、全局技術決策與任務相依；只對有明確正式產物的能力擁有內容。其他能力依橋接映射另行指定唯一可寫所有者。
- 只有倉庫規範強制時才啟用倉庫級必要 Provider，並將其所有權限定為該倉庫的本地合同、實作設計與工作清單。
- 外部 spec、plan、tasks、PRD、architecture 或 story 完整覆蓋對應能力時，本計畫只保留來源、狀態、核准、完整性、唯一所有者、缺口與同步結果，不複製全文。
- 基本必填章節仍保留。被外部產物覆蓋時以可驗證映射表示，不只寫「參考外部文件」。
- 跨倉庫仍只在主倉庫維護一份需求計畫；其他倉庫只更新自身強制產物或實作文件。
- Provider 格式強制重複事實時，寫入前先列出重複、同步責任與不一致風險，由使用者決定。

## 適應性細化與釐清

- 先探索可由環境查證的事實，例如現有入口、合同、資料流、相近實作、測試與文件；不要把可查事實改成使用者問題。
- 只有答案會改變範圍、行為、合同、方案、測試 seam 或驗收時才提問。一次只問一個問題，附建議答案及主要取捨，等待回覆後再進入下一個相依決策。
- 需求已由目前對話與倉庫證據完整回答時不重複提問；小型需求不為展示流程而拉長訪談。
- 存在使用者可觀察行為、多角色、多分支或狀態轉換時，以精簡行為場景補足驗收。純內部且合同單一的改動可移除該條件式小節；不強制產生冗長 User Stories。
- 計畫的詳細度依風險、擴散範圍、相依關係及不確定性調整，不以檔案數單獨判定。資訊不足以形成可實作方案時，保留待確認或決策迷霧，不用虛構步驟填滿文件。

## 文件密度檔位

符合下列全部條件時，使用**小型原生緊湊檔**：

- 單一倉庫、單一責任邊界。
- 沒有活動外部 Provider 正式產物。
- 沒有跨專案缺口、高擴散路徑、實質替代方案或未解決的合同決策。
- 可由一個 `S-*` 垂直切片完成，且驗收、風險與測試 seam 已清楚。

緊湊檔只使用下列六個二級標題，不得再逐章複製完整範本：

1. **基本資訊與目標**：日期／倉庫、計畫狀態、交付狀態、來源／核准、原生 Provider 所有權、問題、目標與 `AC-*`。
2. **範圍、證據與決策**：範圍／非範圍、關鍵 path／symbol 證據、影響、複用結論、方案、不變條件，以及風險／假設／漂移；沒有者在同一區塊以一行依據表示。驗收明示「不得發生」的寫入、通知或其他副作用仍屬具體風險，不得因需求小型而填無。
3. **實作計畫**：用一張表以 `S-*` 同時擁有檔案／symbol、最小修改、對應 `AC-*`、端到端成果、`Blocked by` 與完成判準。每個變更檔案獨立一列；同一切片涉及多個檔案時重複 `S-*`，不把多個 path 合進同一儲存格。
4. **測試與驗證**：測試設計連結、測試 seam、`AC-*`／`T-*` 映射、整體通過標準；不得複製具體命令。
5. **文件與待確認事項**：文件處置與真正會影響交付的問題；無變更紀錄時不建立空表。
6. **實作與驗證結果**：初稿只保留待回填提示。

任一條件不成立時使用**標準／擴展檔**，依完整範本保留必要核心標題，再按證據展開 Provider、行為場景、跨專案、路徑矩陣、詳細複用、替代方案或文件清單。檔位只控制表達密度，不得刪除驗收、範圍、證據、影響、複用、風險、切片、測試 seam、文件處置、核准或結果回填等核心語義。

## 必填章節

下列是每份計畫都要覆蓋的核心語義，不等於每項都必須擁有獨立標題。小型原生緊湊檔依「文件密度檔位」合併，標準／擴展檔才使用完整範本標題。同一事實只由一處擁有；沒有待確認事項、假設或風險時可用一行「無。依據：…」，不展開空表格。`AC-*`、`S-*` 與 `T-*` 從 `01` 起使用至少兩位數零補齊，同一份需求中位數保持一致。

1. **基本資訊／狀態**：主題、日期、負責範圍、計畫狀態、交付狀態、需求來源與前版連結。
2. **Provider 橋接**：原生模式只保留一行所有權；活動外部產物才展開映射。
3. **需求來源與目標**：來源、問題、目標、帶 `AC-*` 的驗收條件與來源缺口。
4. **範圍與非範圍**：本次包含與不包含的責任邊界。
5. **現況與證據**：目前入口、合同、資料流、測試、文件漂移、所屬專案／倉庫與倉庫內相對路徑。
6. **影響分析**：介面、資料、事件、相依服務、相容性與使用者流程。
7. **複用分析**：現有能力與複用決策；小型且結論明確時使用一行摘要。
8. **方案與決策**：選定方案、責任放置與不變條件。
9. **風險**：風險、觸發條件、緩解與驗證方式；沒有具體風險時只保留一行依據。
10. **檔案級實作計畫**：逐檔案列出所屬 `S-*`、專案／倉庫、相對路徑、符號與最小修改。
11. **實作切片**：以 `S-*` 表達端到端成果，映射 `AC-*`、阻塞關係與完成判準。
12. **測試與驗證**：只記錄測試 seam、`AC-*`／`T-*` 映射、整體驗證關卡、主要風險、通過標準與測試設計文件連結。
13. **文件改動**：沒有文件工作時只保留一行依據；需要更新時才展開清單。
14. **待確認事項**：只保留會影響範圍、合同、方案或驗收的問題。
15. **變更紀錄**：記錄事實更正、待核准候選變更、已核准偏差、核准證據與同步結果。
16. **實作與驗證結果**：初稿只保留待回填提示；實作後才依 `S-*`、`AC-*` 與 `T-*` 展開 Diff 對帳、結果、未完成項目、剩餘風險與文件回填。

下列為條件式章節或區塊，只有存在對應證據時保留：

- **Provider 橋接映射**：存在活動外部正式產物時展開；原生模式只保留一行。
- **行為與驗收場景**：存在使用者可觀察分支、角色或狀態轉換時保留。
- **跨專案／職能邊界**：存在具體跨專案缺口或協作邊界時保留。
- **路徑覆蓋矩陣**：高擴散變更時保留。
- **詳細複用候選／未命中搜尋**：存在多個候選、抽取決策或搜尋未命中時保留。
- **替代方案**：存在會影響方案選擇的實質取捨時保留。
- **文件改動清單**：需要更新時才展開；不需要時不產生空 checkbox。

「AI 協作紀錄與成效」不是「實作與驗證結果」的一部分，也不是基本必填章節，預設關閉。只有使用者明確要求 AI 成效／提效，或目標倉庫政策明確要求時才另行加入；啟用後必須使用完整可選範本，不可只加入空標題或猜測數值。

## 複用分析

小型且只有一個明確候選時，以一行記錄所屬專案／倉庫、class、method、相對 path、決策、原因與邊界。存在多個候選、跨專案能力或抽取決策時，才展開表格，並在「複用、擴充、抽取、不複用」中選一項。

找不到可複用能力時，不寫籠統結論；列出使用過的搜尋詞、搜尋路徑與未命中的結果，再說明為何需要新增能力。

## 實作切片與 Wide refactor

- 每個垂直切片使用穩定 `S-*` ID，交付一段端到端可驗證成果，映射至少一個 `AC-*`，並記錄 `Blocked by` 與完成判準。切片描述行為與驗證，不重複檔案級實作計畫；檔案級計畫以 `S-*` 回指切片，只記錄 path、symbol 與最小修改。
- 切片以能在一次合理工作階段內完成並獨立驗證為準；小型需求可只有一個切片，不為形式拆出 Controller、Service、Repository 或測試等水平工作。
- 阻塞關係只保留真正無法提前開始的依賴。沒有阻塞的切片可並行，但仍須遵守同一內容所有者與核准範圍。
- **Wide refactor** 是單一機械變更會同時破壞大量呼叫端、無法保持每個垂直切片獨立可用的例外。此時使用 `expand → migrate → contract`：先加入相容的新形式，再按可回歸範圍分批遷移，最後刪除舊形式。
- 每個 migrate 批次應保持可驗證；只有批次無法單獨保持綠燈時才使用明確整合關卡，並在最終整合切片統一驗證，不把失敗中間狀態冒充完成。

## 高擴散變更與合同值形狀

只有變更共用格式化、正規化、權限、設定或其他會影響多個入口的規則時，才在「影響分析」加入精簡的路徑覆蓋矩陣。依目前程式碼證據列出實際存在的正常入口、舊快取或歷史資料、外部服務／RPC 及 fallback、legacy／管理端／內部／demo、通知與背景任務；逐項記錄可複用能力、旁路風險、驗證方式，以及「修改」「回歸驗證」「非範圍」「待確認」其中一種處置。已經過共用能力的路徑通常標記「回歸驗證」，只傳 ID、不展示資料且確定不受影響的路徑可標記「非範圍」；不要為填滿矩陣虛構入口。

候選值、占位值或原型值替換為正式值時，重新核對欄位／設定名稱、值的語義與形狀、consumer 使用方式、schema／型別、測試 fixture 與文件。例如短 ID 變成完整 URL，不能只驗證「非空」；若 consumer 或相容方式尚未確認，列入待確認事項，不把計畫標記為可實作。

## 架構與分層原則

### 通用判斷

先依根目錄規範、框架與套件設定、目錄慣例及附近模組判定目標範圍的實際架構。計畫需記錄採用的證據、責任放置位置與理由；不同專案或子專案分別判斷，不為統一文件格式強迫重構。

### 後端分層

只有後端專案本身採用 Controller、Logic、Service、Repository，且需求與現況沒有衝突時，才把 `Controller → Logic → Service → Repository` 作為候選鏈路。在該分層下，Repository 原則上只由 Service 呼叫；其他層只有在專案規範或已驗證的強烈理由支持時才直接呼叫 Repository。

### 前端與其他架構

前端、行動端、資料流程及其他架構沿用目標專案的實際責任邊界，不套用上述後端鏈路。page／route、component、hook／composable、store、API client 等名稱只能作為定位線索；只有倉庫規範與程式碼證明存在時，才寫入架構或檔案級計畫，不組合成預設鏈路。

## 測試、驗證與命令回填

需求計畫先選擇使用者可觀察的最高且穩定公開介面，再判斷對應測試 seam 是既有或新增。現成低層測試不能充分驗證可見合同時，不因成本較低便停在該層；應在既有公開介面新增測試。只有較高介面無法可靠觀察關鍵行為時才下移。記錄 seam、既有或新增、選擇理由與核准狀態；計畫整體核准可一併確認 seam，只有存在實質歧義時才另行提問。

需求計畫只定義測試 seam、`AC-*`／`T-*` 映射、驗證關卡、驗證範圍、主要風險、整體通過標準與回歸邊界，並以相對連結指向獨立測試設計文件。詳細測試情境、前置條件、操作步驟、測試資料、目標檔案、具體命令、關鍵斷言與逐案例結果只放在獨立 test-design，不在需求計畫重複維護。

## 計畫落盤

先遵循倉庫既有 `docs/plans/` 命名與格式慣例。沒有慣例時，使用：

```text
docs/plans/YYYY-MM-DD-<topic>.md
```

`topic` 使用簡短、穩定的 kebab-case，不納入易變狀態或人名。不可覆蓋歷史計畫；同名時建立 `-v2`、`-v3`，並在新版本引用前一版與取代原因。

## 狀態、核准與回填

計畫決策與交付進度是兩個獨立狀態，不互相覆蓋：

- **計畫狀態**：`草擬`、`已核准`、`已取代`。
- **交付狀態**：`未開始`、`實作中`、`部分完成`、`已完成`、`已阻塞`。

例如計畫已核准且正在執行時，同時記錄「計畫狀態：已核准」「交付狀態：實作中」。計畫被新版本取代時，計畫狀態改為「已取代」，仍保留當時交付狀態，不用單一欄位丟失其中一種語意。

實作前必須取得明確核准。實作中出現新事實或需偏離計畫時，先列出原方案、新證據、影響與可選方案；確認後更新計畫，再繼續受影響部分。

完成前用完整 Diff 做範圍對帳：每個變更檔案與行為群都要能對應已核准的檔案級計畫或已記錄的核准偏差；同一檔案包含兩組行為時分開對帳。存在未映射變更時，不得標記為已完成，需先拆離或補齊來源、影響、測試設計與核准紀錄。

初稿的「實作與驗證結果」只填「尚未進入實作；完成後依 `S-*`、`AC-*` 與 `T-*` 回填」，不展開空結果表。完成時依專案／倉庫回填範圍對帳、實際變更、對應情境的結果摘要、未完成項目、剩餘風險與文件狀態；具體命令與逐情境結果由測試設計擁有。未完成文件更新或必要驗證時，交付狀態不得標記為「已完成」。

## 計畫變更與同步

對話中出現新資訊時，先依它是否改變已核准內容分類：

- **事實更正**：只補充或修正證據，沒有改變範圍、對外合同、方案或驗收。直接更新正式章節，在變更紀錄寫明來源與同步結果，不需重新核准。
- **待核准候選變更**：新增、刪除、擴張或縮減範圍、合同、方案或驗收。只寫入變更紀錄的候選內容，計畫狀態退回草擬，停止受影響實作；不得先污染正式章節、實作切片或測試設計。
- **已核准偏差**：使用者已明確核准與原計畫不同的實作或合同。記錄核准證據後，先更新擁有該事實的正式章節，再同步檔案級計畫、實作切片、測試設計、風險與文件改動。

候選變更被拒絕時保留簡短決策紀錄，但不寫入正式範圍。候選變更獲得核准後，逐項回填同步結果；任一必要產物尚未同步時，計畫不能恢復為「已核准」或標記完成。測試通過、提交訊息或程式碼已存在都不能取代核准證據。

存在外部工作流時，上述正式章節由 Provider 橋接映射中的「唯一可寫所有者」負責。同步固定依下列順序進行：

1. 事實更正先更新唯一內容所有者，再同步衍生產物。
2. 已核准的範圍、合同、方案或驗收變更，依「內容所有者 → 設計 → tasks／story → 橋接計畫 → 測試設計」同步。
3. 每個必要產物都回填同步結果；任一項失敗或無法驗證時，保留未同步項與影響，不得標記完成。

## 文件改動

依實作所在專案與既有慣例更新文件。既有模組進行迭代時，同步更新相關實作文件；新模組沒有慣例時，提出建議路徑與必要性，取得確認後再新增。

「文件改動」必須二選一：

- **需要更新**：列出所屬專案／倉庫、倉庫內相對路徑與更新內容，使用 checkbox 追蹤完成狀態。
- **無需更新**：移除更新 checkbox，以普通文字寫「無需更新」及判斷依據，不可形成未完成項。

跨專案時，各專案只維護自己的實作文件，需求計畫仍只放在主倉庫。環境提供 `agents-doc-maintainer` 時，可用它檢查與維護模組文件。

## AI 協作紀錄與成效

本章節預設關閉。只有使用者明確要求 AI 成效／提效，或目標倉庫政策明確要求時才加入並啟用計時。啟用後分成兩部分回填，不用需求規模、流程名稱或測試數量直接推導節省工時；計量命令、狀態轉換與安全邊界依[參考計時指南](reference-timing.md)執行。

效率只量化時間；不收集、不估算、不輸出 Token 用量，也不以 Token 多寡推導效率。

### 可驗證貢獻

- **需求規模**：小型、中型或大型，附可檢查的範圍依據。
- **協作範圍**：列出實際使用的需求計畫、測試設計、實作輔助、驗證及 Git Diff 審查。
- **產出與驗證**：摘要實際修改、測試、文件及可重現驗證結果。
- **提前發現與避免返工**：記錄 AI 協作提早識別的具體問題、影響及處置；沒有則填無。
- **人工決策與介入**：記錄仍由使用者確認的合同、取捨、測試資料、驗收或發布決策，避免把全部結果歸因於 AI。

### 效率量化

以「相同需求範圍與品質標準下，已核准計畫的 PERT 人工參考基準與本機計量到的 AI 協作參考耗時」作為預設口徑：

```text
階段人工參考工時 = round((O + 4 × M + P) / 6)
參考節省工時 = 人工參考基準 - AI 協作參考耗時
參考工時節省比例 = 參考節省工時 / 人工參考基準 × 100%
```

- **量化結論**：先寫完整需求或指定剩餘範圍是否可比較及原因，不讓讀者自行比較不同範圍的基準與耗時。
- **計量分段與 ID**：只使用 `start` 回傳的隨機 ID，不自建需求或倉庫索引。同一對話完成後新增的核准範圍使用新分段，不恢復舊狀態。
- **計量範圍**：記錄 `full_requirement` 或 `remaining_delivery`、第一個納入階段與排除階段。剩餘交付結果不得表述為整案提效。
- **計量模式與資料來源**：記錄是否啟用，以及最終使用 session 或 ActivityWatch；Provider 降級時以實際來源為準。
- **計量覆蓋度**：依宣告範圍內的工作是否都被記錄填 `complete`、`partial` 或 `unknown`。只有 `complete` 可計算該段節省工時；範圍內中途啟用、漏記或排除未閉合區間一律不是完整覆蓋。
- **階段級 PERT**：對五個固定階段記錄整數秒 `O/M/P`、範圍、複用、測試、文件與風險依據；不適用階段使用 `0/0/0` 並說明。
- **人工參考基準與鎖定時間**：需求與檔案級計畫穩定後估算，產品實作開始前鎖定。完成後不倒推、不參考實際結果回改。
- **基準指紋**：回填 `baseline` 回傳的指紋，與 `complete` 摘要對帳。不一致時不計算節省工時或比例。
- **AI 協作參考耗時與階段摘要**：只採用 `complete` 的聚合結果，不以對話時間差、Git 提交時間或事後回憶修正。
- **參考節省工時與參考工時節省比例**：只採用腳本輸出的可重現結果；腳本的相容欄位 `efficiency_percent` 在文件中按其公式表述為工時節省比例。負值如實保留，不改寫為提升。
- **可信度、異常與混入工作**：完整閉合且無已知混入時最高為中；未閉合排除、Provider 降級、`yes` 或 `unknown` 皆為低。不以手工秒數掩蓋異常。
- **歸因限制**：數值是 AI 協作情境下的參考值，可能同時受人員熟練度、需求清晰度、既有複用、離線工作與工作環境影響，不宣稱 AI 的單一因果貢獻。
- **狀態清理結果**：摘要回填後先回讀對帳，再記錄 `delete` 是否成功。未對帳前不刪除。

未鎖定有效 baseline 或計量覆蓋度不是 `complete` 時，仍可回填 AI 協作參考耗時與階段摘要，但參考節省工時與比例必須填寫「無法計算」及原因，不填 `0%`。中途啟用時只有在實作前宣告 `remaining_delivery`、排除已開始階段並完整覆蓋剩餘範圍，才可計算該段結果；計時未啟用、跨對話或範圍已無法與 baseline 對齊時，不猜測整體提效。

## 閱讀性與安全

- 結論優先，章節與段落保持短小。
- 事實、假設與問題分開陳述。
- 證據只使用相對路徑與必要識別字。
- 不貼大段程式碼、日誌或來源全文。
- 不在不同章節重複相同背景。
- 範例與占位內容必須虛構，不寫入公司、專案、需求識別碼、內部網址、絕對路徑、憑證或個人資料。
