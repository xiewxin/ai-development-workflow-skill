# Skill 編排合同

本合同定義 `ai-development-workflow` 如何根據平台本輪提供的 catalog 或目前任務已成立的顯式調用上下文，在不削弱原生四種模式的前提下選用、交接、恢復或退出外部 Skill。通用發現、篩選、調用與降級規則只由本文件擁有；[外部工作流約束檔案](workflow-integration.md)只補充已知 Provider 的產物與安全限制。

## 頂層不變量

- **原生完整性**：需求計畫、測試設計、實作、驗證、文件回填與 Git Diff 審查不依賴任何外部 Skill；平台沒有提供 catalog 或沒有候選通過門檻時，仍可完整交付。
- **發現不等於啟用**：能力出現在 catalog 只代表可被評估，不代表已選用、已授權或已執行。
- **平台中立**：主動發現只能讀取平台本輪提供的 Skill catalog metadata；顯式調用只接受平台在目前任務已建立的調用上下文。兩者都不得掃描全部本機 Skill、猜測未提供能力、建立 registry 或自動查找安裝目錄。
- **無隱式擴權**：不得自動安裝、setup、初始化、提交、封存、刪除、遠端寫入或發布。實作核准只涵蓋已揭露的本地修改與驗證。
- **單一規則所有者**：`SKILL.md` 只保留入口與按需導航；Provider 約束檔案不得創造可用性、提升品牌排序或重複本合同。

## 觸發邊界

動態編排只在下列任一條件成立時啟用：

1. 使用者進入需求計畫、測試設計、Git Diff 審查或完整流程任一使用者入口模式。
2. 使用者明確要求跨 Skill 開發交付協調。

使用者直接調用單一外部 Skill，且沒有進入上述四種模式或要求跨 Skill 協調時，本 Skill 不攔截。一般編碼請求也不因平台提供多個 Skill 而自動進入本合同。

## 編排階段與核心能力槽

編排階段是內部能力選用單位，不等於使用者入口模式或計時階段。核心能力槽由本 Skill 穩定定義，catalog 不得動態擴張分類。

| 編排階段 | 核心能力槽 | 既有計時階段 |
| --- | --- | --- |
| 需求計畫 | 事實研究、需求釐清、領域建模、需求規格、方案設計、實作計畫、任務排序 | `requirement_plan` |
| 測試設計 | 測試設計 | `test_design` |
| 實作 | TDD、實作執行 | `implementation` |
| 驗證與修復 | 驗證、問題診斷、修復執行 | `verification_fix` |
| 文件同步 | 文件同步 | `docs_review` |
| Git Diff 審查 | Standards 審查、Spec 審查 | `docs_review` |

新能力尚未形成穩定責任與所有權邊界時採保守擴展：不自動建立新槽，由使用者明確指定或原生流程承接。能力槽依能否獨立授權、擁有產物、驗證及原生回退劃分，不採「一階段一槽」或「一 Skill 一槽」。

## 雙入口與候選快速路徑

能力只從下列入口接入，兩者不得互相偽裝：

- **主動發現入口**：每個編排階段開始時，從平台本輪提供的 Skill catalog metadata 建立低成本階段能力快照。快照在目前階段內保持穩定，進入下一階段時可刷新；catalog 缺失時不建立替代清單，不掃描本機，直接使用原生路徑。
- **顯式調用上下文**：使用者已透過平台在目前任務直接調用能力時，按平台實際狀態接入；不重新發現、不重新排名、不補造 `selected`，也不再次 `invoked`。已發生的調用不等於產物可被消費；在新增副作用或接入交付前，仍核驗工作範圍、授權、產物所有權、返回結果及較保守的 Provider 限制。

主動發現只對目前所需核心能力槽建立候選。metadata 必須明確表達與該槽相符的正向行為或產物；寬泛描述、品牌或 Skill 名稱本身不足，也不使用關鍵詞計分或固定品牌能力表。Provider profile 只有在候選已出現在階段能力快照，或能力已進入顯式調用上下文後才能補充限制。

### 兩階段能力核驗

能力依下列兩階段核驗：

1. **metadata 初篩**：只用階段能力快照辨識與目前階段可能相關的正向能力證據、catalog 身份及平台提供的調用模式。這一步只形成待核驗短名單，不直接建立候選或啟用能力。
2. **完整候選合同核驗**：讀取本合同後，以核心能力槽及能力映射證據正式建立候選。暫定優先組只能依不會被完整合同改寫的使用者明確選擇與活動正式產物延續建立；其餘可能相關候選全部進入同一一般競爭組，不以 metadata 描述粒度預先拆組。再只展開目前最高優先組內完成門檻與決勝所需的同組候選完整合同，確認責任、產物、調用依賴鏈、授權、副作用、精確適配與交接成本；同組選出唯一執行者後停止，整組淘汰才進入下一組。

每一輪依待核驗能力數採用快速路徑：

| 待核驗能力 | 合同展開與出口 |
| --- | --- |
| 0 | 直接 `native_fallback`，不讀 Provider profile 或無關合同 |
| 1 | 只讀該能力完整合同；通過強制合同、可調用門檻與可驗證增益後成為唯一合格候選，不做虛假比較，否則原生回退 |
| 多個 | 只展開目前最高優先組；唯一合格候選出現後停止，多個合格候選才完成同級決勝，整組淘汰才進入下一組 |

能力匹配預設靜默完成。沒有候選通過介入門檻時，不向使用者輸出逐階段 catalog 摘要、淘汰原因或額外編排報告。

同一任務內可做合同證據的任務內復用，但不落盤保存合同快取。下列任一失效條件成立時必須重新核驗：

- 跨任務、跨上下文或長時間等待後恢復。
- catalog 身份、版本證據、調用模式或可用性改變。
- 使用者授權、倉庫強制合同、活動正式產物或所有權狀態改變。
- 候選執行失敗、產物不完整，或既有證據不足以判定副作用。

## 強制合同、可調用門檻與選用

平台或倉庫對受影響範圍明確要求的能力、產物或流程是強制合同。強制合同先於候選排序；Skill 只因出現在 catalog、已載入或已安裝，不構成強制合同。使用者明確選擇也只能在相容候選中優先。

候選與其必要依賴進入排序前，必須整體通過下列可調用門檻：

1. 平台目前可用，且 catalog 身份可確認。
2. 調用模式可履行，不把 User-invoked 假裝成 Model-invoked。
3. 目前授權涵蓋候選的全部必要行為。
4. 副作用、寫入目標與可回復性已確認。
5. 產物所有權不重複，正式產物有唯一可寫所有者。
6. 與平台及倉庫強制合同相容。

通過硬門檻的候選還必須符合可驗證增益：能指出原生流程之外新增、且可由後續產物、驗證或強制規範證明的貢獻。明確方法要求、活動產物延續、必要獨立證據或原生缺口可以構成增益；安裝狀態、品牌及沒有消費者的重複產物不能。

完整合同核驗後，選用優先序固定為：

1. 使用者對相容候選的明確選擇。
2. 延續目前活動正式產物及其唯一所有權。
3. 對目前能力槽最精確、可驗證的匹配。
4. 最小副作用與最低交接成本。

同一最高優先組的候選必須完成足以比較精確適配、副作用與交接成本的合同核驗，才能完成同級決勝；不得因某候選先被讀取、metadata 描述較細或名稱較像目前能力就提前入選。仍無法可靠決勝時原生回退，不隨機選擇、不依名稱排序，也不要求使用者審核內部候選清單。

## 能力槽執行者、能力包與依賴

需求級工作流所有者維護目前需求的正式 spec、plan、tickets 或等價產物鏈；每個需求最多一個。階段能力執行者只承接一項通過選用規則的能力，不因入選取得其他階段或正式產物的所有權。

互不重疊的能力槽可由不同 Skill 承接，但每個能力槽只有一個主執行者，且每份正式產物只有一個唯一可寫所有者。外部能力只提供證據而不擁有正式產物時，由需求級工作流所有者驗證後回填必要證據。

無法拆分調用且同時覆蓋多個能力槽、產物或副作用的 Skill 視為能力包。能力包採全有或全無判定：整體合同、全部依賴、授權與副作用都通過可調用門檻後才能入選，不得忽略未授權步驟或只假裝執行其中一部分。

調用依賴鏈只沿完整候選合同明確聲明的必要 Skill、設定或使用者動作核驗：

- 父 Skill 內部必需且可合法 Model-invoked 的能力併入同一能力包。
- User-invoked 依賴依序產生交接，每一步完成後重新驗證實際產物。
- 不完整依賴、循環依賴、未授權 setup 或遠端副作用使整體候選不合格。
- 不為補依賴掃描本機、不自動 setup，也不從 Provider 名稱推測隱含前置。

## 跨 Provider 能力組合

跨 Provider 不是按品牌拼裝流程。不同 Provider 只有在承接互不重疊的能力槽，或形成明確的上游／下游關係時才能進入同一交付鏈：

- 同一能力槽、寫入範圍或正式產物只保留一個主執行者與一個唯一可寫所有者。
- 能力包不可拆分；若整包與另一執行者重疊，選擇一條完整工作流或原生回退。
- 唯讀第二來源只有在能提供可驗證的獨立增益，且不建立重複正式產物或隱含寫入時才可加入；其證據仍由本 Skill 驗證及收斂。
- 單一工作流已完整、安全且獲授權時走直接路徑，不為展示協調而增加第二 Provider。

每一條跨 Provider 上下游邊都必須建立輕量產物交接合同，至少包含：

1. 上游正式產物的穩定定位、唯一所有者與新鮮度。
2. 下游承接的精確能力與唯讀輸入邊界。
3. 獨立輸出及其唯一可寫所有者。
4. 禁止回寫上游；設計變更先返回上游所有者裁決。
5. 返回驗證與原生替代。

只有跨任務恢復或版本可能混淆時，才為交接增加內容 hash 或等價版本證據；同一任務且定位、新鮮度明確時不為格式完整強制計算。

## 調用模式與顯式交接

Model-invoked 候選通過全部門檻後，可依平台目前合同觸發。觸發前仍須遵守 Skill 自身的必要前置與副作用邊界。

User-invoked 候選不能由模型代替使用者調用。入選後只輸出一項目前動作的顯式調用指示並暫停目前階段，不在同一回合模擬產物或繼續下游工作。指示由平台目前明示的調用機制、catalog 中的準確 Skill 名稱及完整候選合同需要的參數組成，不維護靜態命令列表，也不固定假設斜線命令。

緊湊交接卡包含：

- 使用者目前需要完成的一項動作及其必要原因。
- 一項目前可執行的顯式調用指示。
- 輸入或上游正式產物定位。
- 已確認的副作用與仍需另行授權的動作。
- 預期產物、唯一可寫所有者與完整性判準。
- 恢復條件，以及候選不可用時的原生替代。

同時存在多個 User-invoked 候選時，先完成硬門檻、增益、選用優先序與同級決勝，只顯示唯一入選候選的一項動作，不輸出未篩選候選選單。

## 能力執行生命週期

- 主動發現候選先依 `observed → qualified → selected` 推進。
- Model-invoked 入選者接續 `invoked → returned → consumed`。
- User-invoked 入選者接續 `handoff_pending → returned → consumed`。
- 顯式調用上下文從平台實際已發生的 `invoked` 或 `returned` 狀態接入；不補造 `selected`、不再次 `invoked`，只在繼續副作用或消費結果前補做同等核驗。
- `returned` 只表示結果已返回；只有存在性、完整性、所有權、副作用及目前需求適配通過，且結果實際接入後，才能標記 `consumed`。
- 沒有安全接續時終止於 `native_fallback`；強制合同無合法替代，或副作用／所有權衝突需要裁決時終止於 `blocked`。運行時狀態不等同驗證結果。

### 結果接納判定

外部能力返回後，在同一任務內做一次不落盤的結果接納判定。結果必須可唯一關聯到目前調用及能力槽，並確認存在、完整、適配目前用途，且沒有新增副作用或產物所有權衝突。判定通過只允許下游使用；實際使用前仍保持 `returned`，不新增生命週期狀態。

只有結果實質影響下游產物或決策時才標記 `consumed`。採納、拒絕或暫緩外部建議，只要該內容實際改變下游產物或決策，均構成消費；僅接收、轉述、展示或存檔不得標記 `consumed`。

同一任務內，下游用途改變只重新判定用途適配。能力身份或版本、授權、工作樹、產物所有權或實際副作用改變，或出現無法判定的漂移時，原判定失效，必須重做完整候選合同核驗。

結果缺失、不完整或不適配，但沒有安全問題時，結束該外部路徑並進入 `native_fallback`。授權、身份、安全、所有權或強制合同出現衝突，或是否存在這類衝突無法確定時，進入 `blocked`。

主動發現或 Model-invoked 路徑安全回退時保持靜默。User-invoked 動作已完成但結果未被使用時，只給一則緊湊提示，包含原因、已觀察副作用及原生接續；`blocked` 只呈現一項必要決策。只有被要求或執行正式評估時才展開完整判定證據。

## `to-tickets` 與派生執行工作清單

計畫完成後不預設調用 `to-tickets`。只有候選由平台 catalog 提供並通過選用門檻，或使用者已透過平台形成 `to-tickets` 顯式調用上下文，且長期追蹤、複雜協作或外部 tracker 能提供可驗證增益時，才建立或消費派生執行工作清單；單一倉庫的核准計畫已能連續執行時，直接使用原生實作。

當 `ai-development-workflow` 保持需求級工作流所有者時：

- 正式計畫是 `to-tickets` 的唯讀上游輸入。
- 派生 tickets 擁有執行切片、阻塞關係與進度，但不取得上游計畫的設計維護權。
- 協調層只保存計畫項目或行為情境到 ticket 的必要 ID 映射與追蹤證據，不雙向改寫兩套工作狀態。
- tickets 返回後重新驗證存在性、完整性、所有權及副作用，再決定接續或原生回退。

使用者已直接選擇一條完整 Matt 或其他外部工作流，且其正式產物、安全與授權完整覆蓋需求時，改走直接路徑，由該工作流依自身合同擁有產物；本 Skill 退出多餘橋接。

## 交接層級與最小記錄

同一任務內以不落盤的緊湊交接卡保存暫停點。確定跨任務、跨上下文或長時間等待，且缺少記錄會使後續無法安全恢復時，才把下列最小交接狀態寫入既有變更紀錄或獨立 handoff 產物：

- 階段、能力槽、入選候選身份及顯式調用指示。
- 上游輸入、預期產物、唯一可寫所有者與副作用邊界。
- 暫停原因、恢復條件及原生替代。

恢復時不信任舊交接狀態，重新驗證實際產物、catalog 可用性、合同、授權與工作樹。編排選用預設只在目前任務緊湊說明；除正式產物所有權、跨任務恢復、未解授權或衝突及交付必要證據外，不保存快照、排名、淘汰候選、合同快取或調用統計。

使用者關切門檻固定優先於文件完整性：只有使用者需要執行動作、提供額外授權、裁決正式產物衝突，或跨任務恢復確有必要時，才顯示或持久化編排資訊。使用者不需要關心內部階段能力快照、能力槽名稱、候選排名、淘汰過程或合同復用細節；不得為保存這些資訊新增常駐計畫章節或預設欄位。

## 例外打斷與路徑選擇

能力匹配、合同核驗與安全回退預設在內部靜默完成。只有需要使用者執行 User-invoked 動作、提供額外授權或裁決正式產物衝突時才打斷；不要求使用者逐階段複核內部選用。

- **原生直接路徑**：簡單、低風險且原生流程已完整覆蓋時，不輸出逐階段編排報告。
- **外部直接路徑**：單一外部工作流已安全、完整且獲授權時，交接後退出多餘協調。
- **協調路徑**：跨工作流、授權、產物所有權、恢復或原生降級需要統一處理時，薄型協調層才保持介入。

## 原生回退與安全降級

沒有候選安全通過、候選無可驗證增益、資料不足或無法可靠決勝時，使用原生回退。外部能力失效後先核驗實際狀態，再依下表處理：

| 實際狀態 | 處理 |
| --- | --- |
| 寫入前失效或沒有副作用 | 靜默嘗試下一合格候選；否則原生回退 |
| 留下有效、所有權明確的本地部分成果 | 驗證後從部分成果接續，不重做有效工作 |
| 留下衝突產物、所有權不明、遠端副作用或難回復寫入 | 暫停並呈現恢復狀態；不得盲目重跑、覆寫或回滾 |
| catalog 或完整合同資料不足的可選候選 | 淘汰候選並原生回退 |
| 強制能力資料不足或失效 | 阻斷受影響階段，除非強制合同明示替代路徑 |

安全降級只改變受影響能力，不宣稱未完成的 Provider 已通過，也不把原生接續描述成外部能力成功。

## 編排驗證合同

公開確定性合同只能證明規則、文件結構與安全邊界可重複檢查，不能單獨證明真實行為或效率。指定平台的基礎編排只有下列必要項全部有可復核的 `passed` 證據才可宣稱通過：

- 公開確定性合同通過。
- 一項 Model-invoked 能力到達 `consumed`。
- 一項 User-invoked 交接返回並到達 `consumed`。
- 沒有合格候選時實際發生一次 `native_fallback`。

每個預註冊項目只能使用四種互斥結果：

- `passed`：觀察證據完整且符合標準。
- `failed`：已觀察到違反合同的行為。
- `not_observed`：必要平台條件未自然形成，沒有真實行為結論。
- `insufficient_evidence`：行為已執行，但證據不足以裁決。

運行時不可用不是驗證結果；`blocked` 是生命週期狀態，也不得混入四種結果。同一驗證範圍依 `failed → insufficient_evidence → not_observed → passed` 保留最嚴格結論，只有全部必要項為 `passed` 才通過。

基礎編排與每個具名 Provider 能力分開彙總；通用路徑通過不代表 Matt、Superpowers 或其他整包 Provider 通過，可選 Provider 的失敗也不連帶否定已獨立通過的基礎範圍。缺少自然條件時不得安裝、掃描或以合成能力補成通過；合成 fixture 只驗證通用合同。

## 審查收斂

外部 `code-review` 或其他 reviewer 可分別提供 Standards／工程品質與 Spec／範圍原始證據，但不擁有最終問題生命週期。`ai-development-workflow` 固定擁有審查收斂：依目前程式碼、完整 Diff、需求與可重現驗證確認、去重並正規化為單一 `REV-*` 清單。

Model-invoked 審查完成但不擁有正式產物時，只回填實際交付證據，不持久化 Provider 排名、候選歷程或完整原始輸出。

## Provider 約束檔案的邊界

[外部工作流約束檔案](workflow-integration.md)只在候選已出現在階段能力快照，或能力已進入顯式調用上下文後，補充已知產物鏈、前置條件、所有權與更保守的安全限制。候選完整合同或顯式調用能力的實際合同與 Provider 約束衝突時採較保守者；未知工作流只要完整合同足以確認能力、所有權與副作用，也可依本合同參與。

Provider 約束檔案不得創造可用性、固定品牌優先級、觸發安裝或取代平台 catalog。主動發現入口中，平台未提供對應 Skill 時，已知 profile 只保留為靜態知識，不產生候選或使用者提示；此規則不否定平台目前任務已成立的顯式調用上下文。
