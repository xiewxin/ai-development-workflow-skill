使用本指南時，先讀取並明確連結[測試設計範本](../assets/test-design-template.md)。範本是完整欄位目錄；先選擇文件密度檔位，再保留核心語義與適用的條件式內容，不要求小型需求逐章複製完整骨架。更新既有文件時，遵循專案既有格式與章節慣例。

## 文件邊界

- 需求計畫中的測試章節只記錄測試 seam、`AC-*`／`T-*` 映射、整體驗證關卡、範圍、風險與通過標準。
- 獨立測試設計是詳細情境、前置條件、步驟、預期結果、測試資料、目標自動化、具體命令、邊界與回歸範圍的唯一來源。
- 實際 Task 狀態、命令、測試結果、commit SHA、偏差與累計驗證只由同計畫包的 `execution.json` 擁有；核准後不為回填結果修改 `test-design.md`。
- 執行命令的 `planned_run_id` 引用本文件 RUN ID；每次觀測使用唯一 `run_id`，測試結果引用該觀測 ID，保留 RED、GREEN、重試及累計驗證的獨立證據。
- 測試設計只引用目標測試路徑，不放完整測試程式碼；只有在澄清關鍵斷言或資料流時，才使用極短偽碼或片段。
- implementation 為直接執行而完整摘錄 `RUN-*` 命令與 Expected 時，仍以本文件為唯一來源；核准前逐字對帳，不能另行決定命令。正式文件內的設計狀態與橋接完整性是核准前快照，之後的狀態變化只記錄 execution。

## Provider 橋接

原生模式只保留一行「本文件擁有詳細測試設計」，刪除完整 Provider 映射表。只有[Skill 編排合同](skill-orchestration.md)已確認需求級工作流所有者或階段能力執行者，且存在活動測試產物時，才依[Provider 約束檔案](workflow-integration.md)展開測試橋接。主倉庫保留計畫包內的 `test-design.md` 作固定入口，其他倉庫不自動建立重複測試設計；舊 `<topic>-test-design.md` 僅作 legacy_flat 歷史讀取。

橋接區塊需記錄需求級工作流所有者、相關階段能力執行者、需求／驗收與案例映射、產物定位、狀態／完整性、唯一可寫所有者、讀寫權、同步方向與同步結果。產物定位使用倉庫內相對路徑或 tracker 識別字；外部產物完整時只保留索引與本次驗證結果，不複製案例全文；不完整時只補下列缺口：

- 需求／驗收與外部案例或穩定 ID 映射。
- P0／P1／P2／P3 測試情境優先級與風險排序依據；這不是 Skill 候選排名。
- 測試資料建立、隔離與清理策略。
- 自動化目標相對路徑、測試名稱、執行位置、命令與關鍵斷言。
- 手動／環境驗證與必要的參數化唯讀 SQL。
- `execution.json` 的 `T-*`／`RUN-*` 證據映射、缺口與交付阻斷狀態。

可選 Provider 的測試產物失效時，橋接入口可補全為原生測試設計；強制 Provider 的必要測試產物失效時，阻斷受影響交付，只能使用規範明示的替代路徑。

## 按需求規模裁剪

預設產出能直接執行的最短版本，不以篇幅代表完整性。先覆蓋明確需求與具證據的高風險，再依規模選擇結構：

- **小型**：單一入口、有限合同或少量驗收情境。優先用緊湊表格；四個驗收情境通常應在約 100 行內交付。
- **中型**：涉及多個責任層、合同或測試層級。可依模組拆表，但只拆解確有不同前置條件或驗證方式的部分。
- **大型**：跨專案、多資料流或多階段交付。才按專案、流程或風險分節，並保留跨專案執行位置。

同一事實只寫一次，其他章節以穩定 ID 或相對連結引用：

- 「範圍與策略」只界定目標、邊界與方法，不重列逐案例預期。
- 「測試資料策略」以 `D-*` 作為資料建立、隔離與清理方式的唯一來源，可由多個 `T-*` 共用。
- 「詳細情境」以 `T-*` 作為行為、前置條件、步驟、預期結果、優先級與回歸保護的唯一來源，並映射需求計畫的 `AC-*`。
- 「目標自動化映射」是預計測試檔案與名稱、mock／外部邊界、關鍵斷言的唯一來源；以 `RUN-*` 指向執行位置、預計命令與預期輸出。
- 「回歸」只記錄跨情境或既有套件的回歸方式，引用 `T-*` 與 `RUN-*`，不複製內容。
- 「交付測試清單」只記錄 `T-*`、驗證類型、`RUN-*` 或替代方式與交付阻斷標準，不重述步驟、資料、檔案、命令或結果。
- 「執行證據索引」只指向同目錄 `execution.json`，不複製實際檔案、命令、結果或偏差。

## 文件密度檔位

需求計畫已判定為小型原生緊湊檔，且測試只使用一個公開 seam、一組可控資料來源與一個執行命令時，測試設計也使用**小型原生緊湊檔**，只保留下列五個二級標題。`T-*`、`D-*` 與 `RUN-*` 從 `01` 起使用至少兩位數零補齊，並與需求計畫的 `AC-*`、`S-*` 位數一致：

1. **基本資訊與策略**：日期／倉庫、設計狀態、計畫回鏈、`execution.json` 證據連結、原生 Provider 所有權、範圍、策略、環境、測試 seam 與 `AC-*` 映射。
2. **測試資料與情境**：以 `D-*` 定義資料／隔離方式，並以單一 `T-*` 表記錄驗收、步驟、可觀察預期、優先級與回歸保護。
3. **自動化與執行**：目標檔案／名稱、mock 邊界、關鍵斷言，以及唯一擁有具體命令的 `RUN-*`；無手動、環境或 SQL 驗證時只用一行說明，不另建標題。
4. **回歸與交付**：跨情境回歸、完整套件及 `T-*`／`RUN-*` 交付阻斷標準。
5. **執行證據與未覆蓋風險**：只連結 `execution.json`，並保留核准前已知但未覆蓋的設計風險。

存在多個 seam、不同資料生命週期、多個執行環境／命令、手動或 SQL 驗證、外部 Provider 產物、跨專案邊界或大量情境時，使用**標準／擴展檔**。檔位只合併標題，不得省略設計狀態、`AC-*`、`T-*`、適用的 `D-*`／`RUN-*`、關鍵斷言、回歸、執行證據索引與未覆蓋風險。

## 建立時機

- 完整流程中，在 `design.md` 與 `delivery.md` 內容穩定後建立，並於整包最終核准前完成；四份正式 Markdown 一次進入最終核准。
- 使用者只要求測試設計時，可獨立建立，不得立即新增或修改目標專案的實際測試目錄。
- 只有進入已核准的實作階段，才在目標專案實際採用的測試目錄建立或修改測試。`/tests` 只代表該實際目錄，不固定代表 `tests/Unit`。

文件只保存**設計狀態**：`草擬`、`已核准`、`已取代`。執行狀態屬 `execution.json`；設計已核准但尚未執行時，不在本文件複製動態狀態。

## 存放與連結

新生成測試設計固定放在需求計畫包內：

```text
docs/plans/YYYY-MM-DD-<topic>/test-design.md
```

- `topic` 使用簡短、穩定的 kebab-case。
- 不覆蓋歷史文件；同名計畫包建立 `-v2`、`-v3`，並說明取代原因。舊平鋪 `<topic>-test-design.md` 只作相容讀取。
- 測試設計、需求計畫與需求來源必須互相連結；無法直接連結的來源，記錄可追溯的中立摘要與缺口。
- 跨專案需求預設只在主倉庫維護一份測試設計。每筆目標測試、證據與命令都要標示專案／倉庫，以及倉庫內相對路徑或執行位置。

## 情境設計

先逐項覆蓋需求明確指定的驗收情境，再檢查正常、邊界、無效、異常、權限、相容性與回歸中哪些確實適用。不得為展示完整性主動新增需求未要求的案例；只有目前程式碼證據顯示下列明確風險時才補充，並在情境中用一句話標示證據路徑或 symbol：

- 安全風險。
- 資料正確性風險。
- 主要副作用風險，例如重複寫入、漏寫或錯誤狀態轉換。
- 高回歸風險，例如已驗證的既有呼叫端或關鍵相容合同。

每個適用情境使用唯一 `T-*`，並必須包含：

1. 對應的 `AC-*`、需求或具體風險。
3. 前置條件。
4. 可重現的操作步驟。
5. 可觀察的預期結果。
6. 驗證類型：自動化、手動、環境或上線觀察。
7. 優先級與排序依據。
8. 需保護的回歸範圍。

優先級先沿用目標專案既有尺度；專案沒有定義時，使用下列測試排序語意：

- **P0**：安全事故、不可逆資料損毀或服務不可用風險，最先驗證並阻斷交付。
- **P1**：核心驗收、主流程或對外合同，交付前必須驗證。
- **P2**：適用的邊界、錯誤、相容性、主要副作用或高回歸風險。
- **P3**：低風險補充或觀察性驗證，不影響已明確要求的驗收範圍。

每個情境都要附排序理由；優先級只決定順序，不得用來刪除需求明確指定的情境。

小型需求預設每個情境一列，只有單列無法清楚表達多步驟、不同環境或多個可觀察結果時才展開子章節。手動、SQL、權限、環境與上線觀察全部不適用時，整個對應章節只寫一行「無。依據：…」。

不得因時限、主管壓力或交付壓力，擅自刪除需求中的無效、過期、未提供或其他驗收條件。若指令與驗收條件衝突，列出受影響情境、回歸風險與可選方案，再請使用者確認。

## 自動化映射

依目標倉庫實際的 test runner、測試目錄與鄰近測試設計，不強迫使用特定框架或 `tests/Unit`。

為框架管理、容器建立或執行期改寫的類別設計測試 seam 時，先記錄下列最小預檢：

1. 讀取鄰近測試與 runner 設定，確認實際使用的測試風格、bootstrap、process isolation 與執行命令，不只依賴套件名稱判斷。
2. 確認目標類別是否經過 AOP、代理生成、容器替換、alias／overload mock 或其他載入期改寫；若後續實作需要刷新生成物，在測試設計中只記錄倉庫已驗證的安全命令，不在此階段執行刷新。
3. 核對預計採用的 mock／替身方式能否與 runner、bootstrap、process isolation 及既有載入順序共存；不以反覆切換 mock 技巧代替相容性確認。
4. 在測試設計中定義一個能證明 seam 可用的最小案例及其 `RUN-*`；取得實作核准後，先建立並執行該案例，再擴展完整情境矩陣。最小案例仍失敗時，保留失敗證據並重新選擇較穩定的可觀察 seam，不在同一假設上堆疊測試。

測試設計階段不建立或執行測試程式碼；上述實際刷新、案例建立與命令執行都屬於取得實作核准後的工作。

一般純函式、既有穩定 fixture 或沒有上述框架載入邊界的測試，不為形式增加預檢表；只需在自動化映射中記錄實際 runner 與鄰近慣例。

每個自動化情境都要在一張緊湊表格映射：

- 專案／倉庫與預計採用的測試檔案相對路徑。
- 測試名稱或命名規則。
- mock、外部依賴與時間、亂數或網路邊界。
- 關鍵斷言，不只是方法被呼叫。
- 對應的 `RUN-*`。

每個 `RUN-*` 在獨立執行映射表中記錄專案／倉庫、相對執行位置、可重現命令或方式、覆蓋的 `T-*` 與預期輸出。相同命令只記錄一次，由多個情境共用；需求計畫只引用 `T-*` 和整體通過標準，不複製 `RUN-*` 命令。

資料建立與清理只在「測試資料策略」以 `D-*` 定義，並列出覆蓋的 `T-*`。相同資料、檔案、命令或 mock 邊界可合併記錄一次，再由穩定 ID 對應；不要為每個案例複製共同設定。

不要求所有情境都自動化。無法自動化時，說明技術、成本、環境或觀測性限制，並指定手動、環境或上線觀察的替代驗證。

## 測試資料

優先級由高到低：

1. mock、factory、fixture、測試專用 seed 或測試自行建立的可控資料。
2. 由 transaction rollback 隔離與回復的測試資料庫資料。
3. 受控、可版本化且可重建的環境 seed。
4. 不得已才使用既有除錯資料，並記錄來源、適用環境與失效風險。

禁止使用正式環境資料、個人資料與脆弱的固定 ID。自動化測試也應先找合適資料，但仍優先自行建立可控資料，不依賴偶然存在的環境狀態。

## 手動驗證與唯讀 SQL

手動驗證需要資料時：

- 依實際 Model、Repository、migration 或 table schema 證據撰寫查詢，不猜測表名與欄位。
- 標示專案／倉庫、相對證據路徑、執行環境、參數、預期條件與讀取範圍。
- 預設只提供參數化 `SELECT`，只取驗證所需欄位，不顯示憑證、個資或其他敏感欄位。
- 測試設計不產出 `INSERT`、`UPDATE` 或 `DELETE`。若情境需要建立或修改資料，只記錄需由使用者依目標專案既有流程另行處理，以及必要的前置條件與清理要求。

無手動 SQL 或無某類驗證時，使用普通文字寫「無。依據：…」，不保留未勾選項目假裝尚未完成。

同樣規則適用於手動、權限、環境與上線觀察；這些類別與 SQL 全部不適用時，整個章節只保留一行依據，不展開空表格、空欄位或未完成清單。

## 執行證據邊界

`test-design.md` 必須保留「執行證據索引」並使用相對連結指向同目錄 `execution.json`。實作與驗證後：

1. `test-design.md` 保持核准時的策略、`T-*`、`D-*`、`RUN-*`、預期結果與阻斷標準，不以實際結果改寫設計。
2. `execution.json` 逐 Task 記錄實際測試檔案、實際命令、exit code、`T-*`／`RUN-*` 結果、偏差、替代驗證與剩餘風險。
3. 實際方式改變測試 seam、驗收、資料生命週期或阻斷標準時，停止受影響實作，退回計畫包草擬並重新核准；單純記錄觀測結果不改 plan hash。
4. `execution.json` 缺少必要結果時，不得宣稱測試交付完成；不得把缺口回填到本文件以規避執行證據要求。

## 交付測試清單

交付清單只用一張表列出 `T-*`、驗證類型、`RUN-*` 或替代方式與交付阻斷標準。實際狀態、檔案、名稱、命令與結果統一回填 `execution.json`。測試程式碼隨實作程式碼交付，清單不再次描述步驟、資料、限制或風險。

## 閱讀性與安全

- 互動語言跟隨使用者；測試設計與測試程式碼依目標倉庫規範，沒有明文規範時跟隨附近檔案慣例。語言策略不影響短章節與可掃描表格的要求。
- 預設先刪除重複內容，再考慮增加章節；小型需求不因範本欄位而膨脹。
- 步驟只寫可執行動作，預期結果只寫可觀察證據，避免長段背景與重複說明。
- 公開內容只使用虛構、中立資訊；不放入真實公司、專案、需求 ID、內部 URL、本機絕對路徑、憑證或個人資料。
